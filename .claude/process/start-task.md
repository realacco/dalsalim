# 작업을 여는 절차

`/task` 로 불려 왔거나, **관문 훅에 막혀서** 여기로 왔을 것이다. 어느 쪽이든 같은 순서를 밟는다.

지름길을 찾지 마라. 브랜치 이름만 맞춰서 훅을 통과하는 건 훅을 만든 이유를 지우는 것이다.

---

## ① 어느 기능인지 정한다 — 먼저 문서를 연다

**이 단계를 건너뛰지 않는다.** 코드부터 보면 "지금 있는 것"에 생각이 갇힌다.

1. `docs/04-기능-정의서-인덱스.md` 에서 기능을 찾는다.
   - 사용자가 말한 것과 가장 가까운 행. 도메인(`session` `family` `fixed-expense` `book` `entry`)으로 좁힌다
   - 파일을 알고 있다면 그 파일 맨 위 `// 기능:` 주석에서 ID 를 읽는다
2. 그 행의 **Notion 링크를 연다** (`notion-fetch`). 동작 명세가 거기 있다.
3. 하드룰 칸에 `H*` 가 있으면 **CLAUDE.md 의 해당 하드룰을 같이 읽는다.**
4. 기획서 절이 걸려 있으면 그것도 연다.

**기능이 인덱스에 없으면 새 기능이다.** 사용자에게 확인받고, Notion 에 페이지를 만든 뒤
인덱스에 행을 넣는다. 순서가 반대면 `Feature:` 트레일러가 커밋 훅에 막힌다.

## ② 지금 코드가 어디까지 와 있는지 본다

```bash
grep -rn "F-FAM-05" server/src mobile/src     # 이 기능이 사는 파일
git log --format='%(trailers:key=Feature,valueonly)' -5 -- <경로>
```

문서와 코드가 다르면 **CLAUDE.md 「명령이 문서와 다를 때 — 네 갈래」** 로 간다.
기획서·하드룰과 어긋나면 **여기서 멈추고 묻는다.**

## ③ 태스크를 산정하고 — 사용자에게 확인받는다

문서와 코드의 차이를 할 일 목록으로 만든다. 그리고 **보여주고 승인을 받는다.**

에이전트가 뽑은 목록은 **초안이지 계획이 아니다.** 그럴듯해 보이는 것이 이 단계의
실패 방식이라, 이슈로 굳히기 전에 사람이 한 번 본다. 여기서 한 번 멈추는 게 절차의 값어치다.

## ④ 이슈를 만든다

```bash
GH="/c/Program Files/GitHub CLI/gh.exe"     # PATH 에 없다
"$GH" issue create --title "[F-FAM-05] 참여 요청 승인·거절" --label family --body "..."
```

- **기능 하나에 이슈 하나.** 안의 작업은 본문 체크박스로 둔다 (`.github/ISSUE_TEMPLATE/feature.md`)
- 라벨은 도메인 하나

## ⑤ 브랜치를 만든다

```bash
git switch -c feat/F-FAM-05-approve-join
```

`feat/` 는 기능 ID 가 필수다. 고쳐야 할 게 기능이 아니면 (오타 · 의존성 · CI · 문서)
`chore/` `docs/` `ci/` `deps/` 로 열면 ID 없이 지나간다 — 그게 정식 탈출구다.

## ⑥ 작업하고 커밋한다

```
feat(family): 승인하면 장부 정원을 다시 센다

왜 이렇게 했는지.

Feature: F-FAM-05
Closes #12
```

- **하드룰을 건드렸으면 테스트 케이스를 추가해야 완료다.** 케이스 이름은 `★ F-FAM-05 …`
- 화면을 건드렸으면 에뮬레이터에서 눌러본다 (3층). 1·2층이 통과해도 커서·키보드는 안 잡힌다

## ⑦ PR 을 올린다

`.github/pull_request_template.md` 가 묻는 두 칸을 **문장으로** 채운다 —
"기능 정의서와 다르게 간 것"과 "눌러본 화면". 없으면 "없음"이라고 쓴다.

CI 가 초록이면 머지하고, 이슈는 `Closes #` 로 닫힌다. **닫힌 이슈는 다시 보지 않는다.**
