# 달살림 MVP 기획서

> v2.0 · 2026-08-31 · **이 문서는 MVP 기획서다.**
> 완성된 제품의 설계도가 아니라, **빠르게 만들어 몇 달 써보고 방향을 잡기 위한 최소 범위**를 정의한다.
> 여기서 정한 것 중 상당수는 실제로 써본 뒤 바뀔 것을 전제로 한다.

---

## 0. 한 줄

**우리 가족, 한 달 살림을 폰으로 같이 적는다.**

**달** = 매달. 이 앱의 단위는 하루가 아니라 한 달이다.
**살림** = 가족이 함께 꾸리는 생활. 혼자 쓰는 장부가 아니라 같이 채우는 장부.

---

## 1. 왜 만드는가 — 실제로 겪은 불편

### 1-1. 지금은 엑셀로 쓴다

가족 가계부를 엑셀로 쓰고 있다. 그 과정은 이렇다.

1. 템플릿을 **직접 만든다**
2. 매월 **시트를 복사한다**
3. 복사한 시트에 값을 채운다

문제는 3번이 아니라 **1·2번과 "엑셀이라서" 생기는 제약**이다.

| 불편 | 실제로 무슨 일이 일어나는가 |
|---|---|
| 템플릿을 매번 만들어야 한다 | 항목이 바뀌면 수식이 깨지고, 그 달만 예외 처리를 하게 된다 |
| 매월 시트를 복사해야 한다 | 복사를 깜빡하면 그 달은 그냥 안 적힌다. 시작 자체가 마찰이다 |
| **폰으로 못 한다** | 엑셀은 데스크톱을 켜야 한다. 그런데 돈 얘기는 폰을 보다가 나온다 |
| 값이 있어도 **왜**가 없다 | 관리비가 6만원 오른 게 시트에 남아 있어도, 이유는 아무 데도 없다 |

**결국 "데스크톱을 켜야 한다"가 가장 크다.**

### 1-2. 그래서 만들려는 것

> 엑셀에서 하던 걸 **폰에서 편하게** 하게 만든다.

- 템플릿 만들기 → **초기에 고정비 항목을 한 번 등록**하면 끝. 매달 그게 템플릿이 된다
- 시트 복사 → **[이번 달 기록하기] 버튼 하나.** 지난달 값이 이미 채워진 채로 열린다
- 데스크톱 → **폰 앱**
- 왜가 없다 → **금액이 달라진 줄에만 사유를 필수로 받는다**

### 1-3. 자동 연동은 일부러 안 한다

이 앱은 카드/계좌를 연결해서 자동으로 긁어오지 않는다. 못 해서가 아니라 **의미가 없다고 판단해서**다.

자동 등록을 해도 결제처 상호명만 봐서는 그게 뭐였는지 모르는 경우가 태반이다. 결국 사람이 열어서
"이건 뭐였지"를 판단하고 고쳐 적게 된다. 상호명만으로 분류가 깔끔하게 되는 건
경험상 **10건 중 3건 정도**고, 나머지 7건은 어차피 손이 간다.

> **그럴 거면 처음부터 직접 적는 걸 잘 도와버리자는 jpark의 생각.**
> 자동 분류를 반쯤 해주고 나머지를 사람에게 떠넘기는 것보다,
> 물어볼 걸 정확히 물어보는 게 낫다.

이 판단의 부수 효과 하나: **금융 데이터 연동이 없으므로 마이데이터 같은 라이선스가 필요 없다.**

### 1-4. 설계 원칙 — 차이에만 이유를 묻는다

고정비는 매달 거의 같다. 같으면 물어볼 게 없다. **다를 때만 묻는다.**

```
관리비   [ 180,000 ]  ← 지난달과 같음. 그냥 다음.
관리비   [ 240,000 ]  ← 6만원 더 나왔네? "왜 이랬어?" (필수 입력)
```

이 한 줄의 사유가 6개월 뒤 "작년 여름에도 이랬네"를 만든다.
**달살림이 쌓는 진짜 자산은 금액이 아니라 사유다.** 엑셀에는 이게 안 남는다.

## 2. 누가 쓰는가

| 역할 | 설명 | 권한 |
|---|---|---|
| **가족장(OWNER)** | 가족을 만든 사람 | 초대코드 재발급, 멤버 관리 |
| **가족원(MEMBER)** | 초대코드로 참여 | 고정비 관리, 본인 월간 기록 작성 |

권한은 거의 나누지 않는다. 가족은 서로 신뢰하는 관계고, 권한 분리는 갈등을 만들지 신뢰를
만들지 않는다. **되돌리기 어려운 작업만 OWNER 전용**이다.

가족 규모 가정: **2~5인.** 부부 2인이 가장 흔한 케이스.

## 3. 핵심 개념

```
가족(Family)
 └─ 멤버(Membership)              아빠, 엄마, 나
     └─ 고정비 항목(FixedExpense)   "아빠의 통신비 55,000원"   ← 엑셀의 '템플릿'

월 장부(MonthlyBook) = 가족 × 특정 월 (2026-08)              ← 엑셀의 '이번 달 시트'
 └─ 개인 기록(MemberEntry)         멤버 1명이 그 달에 쓴 기록
     └─ 입력 줄(EntryLine)          수입 / 고정비 / 추가지출 각 한 줄
```

### 왜 고정비를 "사람별"로 두는가

같은 "통신비"라도 아빠 것과 내 것은 다른 금액이고 다른 사람이 낸다.
가족 합계만 보면 "통신비 18만원"인데, 이건 아무 대화도 만들지 못한다.
**사람별로 쪼개야 "내 통신비가 왜 이렇게 비싸지?"라는 질문이 생긴다.**

### 월 장부는 "완성"을 강제하지 않는다

가족 전원이 제출하면 장부에 **완성** 표시가 붙는다. 하지만 그건 **표시일 뿐 잠금장치가 아니다.**

> **v2.0에서 바뀐 것:** 이전 기획은 "전원 제출해야 요약이 열린다"였다. 이걸 뺀다.
> 한 명이 안 쓰기 시작하면 그 달부터 아무도 아무것도 못 보게 되는데,
> 시행착오를 겪어보려는 MVP 단계에서 그 잠금은 순전히 손해다.
> **요약과 추이는 언제나 열려 있고, 대신 "엄마가 아직 안 적었어요"를 항상 같이 보여준다.**

| LLM 월간 요약 | 재료(사유·특이사항)가 몇 달 쌓여야 요약할 게 생긴다 |

### 아예 안 하는 것

| 안 하는 것 | 이유 |
|---|---|
| 카드/계좌 자동 연동 | 1-3의 판단. 설계 원칙에 정면으로 반한다 |
| 영수증 촬영 / OCR | 항목 단위 앱이다. 영수증은 거래 단위 도구다 |
| 예산 설정 · 초과 경고 | 잔소리 앱이 되면 가족이 안 쓴다. 달살림은 판단하지 않고 보여준다 |
| 절약 점수 / 등급 / 랭킹 | 게임화는 가족 사이에서 역효과다 |
| 자산 · 투자 관리 | 다른 제품이다 |

## 5. 개인 가계부 (v0.2 — 개념만 확정)

가족 장부는 **항목 단위**다. "식비 620,000" 한 줄이면 충분하다.
그런데 그 62만원을 **세부까지 적고 싶은 사람**이 있다. 그건 가족 장부에 넣으면 안 된다.
가족 전체가 남의 커피값 목록을 보게 되면, 그 순간 아무도 솔직하게 안 적는다.

그래서 층을 나눈다.

```
가족 장부   항목 단위   "식비 620,000"                 가족 전원이 본다
   ↑ (선택적으로 합계만 올린다)
개인 장부   세부 단위   "점심 9,000 · 커피 4,500 …"    기본은 나만 본다
```

- 개인 장부는 **기본이 비공개**다. 공개는 **명시적인 선택**이어야 한다
- 공개 단위는 줄이 아니라 묶음이다: `비공개` / `합계만 공유` / `전부 공유` 셋 중 하나
- 개인 장부의 합계를 가족 장부의 한 줄로 **올려보낼 수 있다** (자동 반영이 아니라 버튼)

> 데이터 모델 관점에서 미리 지켜둘 것: `EntryLine`에 나중에 `visibility`와
> `parentLineId`를 얹을 수 있게 남겨둔다. 지금 컬럼을 만들 필요는 없다.

## 7. 화면별 상세

### 7.1 로그인

- 버튼 하나: **카카오로 시작하기**
- 약관·개인정보 동의는 카카오 동의 화면에 위임한다
- 개발용 로그인은 서버가 `DEV_LOGIN=true`일 때만 노출된다 (운영에서는 라우트 자체가 없어야 한다)

### 7.2 가족 만들기 / 참여하기

한 화면에 두 갈래.

**만들기** — 가족 이름("김씨네") + 내 표시 이름("아빠") → 6자리 초대코드 발급 (`K7QM3D`)
**참여하기** — 초대코드 6자리 + 내 표시 이름 → 참여

표시 이름은 카카오 닉네임과 별개다. **가족 안에서 불리는 이름**이다.

> **왜 딥링크가 아니라 초대코드인가:** 딥링크 초대는 유니버설 링크 + 앱 미설치 폴백까지
> 구현 비용이 크다. 6자리 코드는 카톡 복붙 한 번이면 되고, 가족은 어차피 같은 카톡방에 있다.

### 7.3 탭 1 — 이번 달

- 상단: `2026년 8월` (좌우 화살표로 월 이동)
- 내 상태 카드
  - 미작성 → **[이번 달 기록 시작하기]**
  - 작성 중 → **[이어서 작성하기]** + 진행률 (3/7)
  - 제출 완료 → 내 요약(수입/지출/남은 돈) + [수정하기]
- 가족 진행 현황 (사람별 ✅ / ✍️ / ⬜)
- **[8월 요약 보기]는 항상 눌린다.** 다만 미제출자가 있으면 요약 위에
  `엄마가 아직 안 적었어요 — 아래 숫자는 2명 기준입니다`를 띄운다

### 7.4 탭 2 — 고정비 (= 엑셀 템플릿을 대체하는 화면)

사람별로 묶인 리스트.

```
아빠
  통신비        55,000원   매월 25일
  자동차보험    83,000원   매월 5일
  + 항목 추가

엄마
  통신비        43,000원   매월 25일
  + 항목 추가
```

항목 편집: 이름 / 분류 / 기본 금액 / 결제일(선택) / 사용 여부
삭제는 실제로 지우지 않고 `active=false`다. **과거 기록이 그 항목을 참조하고 있기 때문이다.**

**분류 — 고정 목록 9개:**
`주거` `통신` `보험` `교통` `구독` `교육` `대출·상환` `생활` `기타`

> 사용자가 분류를 직접 만들게 하면 가족마다 제각각이 되어 나중에 추이 비교가 무너진다.
> 고정 목록으로 시작하고, 부족하면 목록을 늘린다.

### 7.5 탭 3 — 추이 (v0.1 신규)

엑셀에서 못 하던 것이 아니라, **엑셀에서 하려면 시트를 다 뒤져야 했던 것**이다.

```
       수입 ── 고정비 ── 남은 돈
 500만 ┤    ╭─────────────╮
       │ ───╯             ╰───
 250만 ┤ ───────────────────
       │ ╭───╮   ╭───╮
   0   └─────────────────────
        3월 4월 5월 6월 7월 8월
```

- 최근 12개월, 라인 3개 (수입 / 고정비 합계 / 남은 돈)
- 아래에 월별 표 — 탭하면 그 달 요약으로 이동
- 데이터가 2개월 미만이면 차트 대신 `두 달째부터 추이가 보여요` 안내

**이 화면은 두 번째 달부터 의미가 생긴다.** 첫 달에는 비어 있는 게 정상이다.

### 7.6 탭 4 — 가족

- 가족 이름, 멤버 목록(표시 이름 + 역할)
- 초대코드 표시 · 복사 · 재발급(OWNER)
- **가족 나가기** / **멤버 내보내기**(OWNER) / **가족장 이양**
- 로그아웃

### 7.7 ★ 스텝 입력 위저드 (이 앱의 심장)

한 화면에 **질문 하나.** 상단에 진행 바.

#### 스텝 1 — 수입

```
┌─────────────────────────────┐
│ ●────────────────  1 / 7    │
│                             │
│  이번 달 수입은              │
│  얼마나 들어왔나요?           │
│                             │
│      3,200,000 원           │  ← 지난달 값이 기본으로 채워져 있음
│      지난달과 같아요          │
│                             │
│            [ 다음 ]          │
└─────────────────────────────┘
```

기본값과 **다르게 고치면** 그 자리에서 사유 칸이 펼쳐진다.

```
│      3,450,000 원              │
│      지난달보다 250,000원 많아요  │
│  ┌──────────────────────────┐  │
│  │ 왜 달라졌나요?             │  │  ← 필수
│  │ 상여금 나옴                │  │
│  └──────────────────────────┘  │
```

#### 스텝 2..n — 고정비 항목

등록한 고정비를 **한 항목씩** 보여준다. 기본값 우선순위:

1. **지난달에 내가 실제로 적은 금액** (`plannedSource = LAST_MONTH`)
2. 없으면 고정비 항목의 등록 금액 (`FIXED_DEFAULT`)
3. 둘 다 없으면 빈칸 (첫 달 — 비교 대상이 없으니 사유도 안 묻는다)

```
┌─────────────────────────────┐
│ ●●●─────────────  3 / 7     │
│  통신                        │
│  통신비                      │
│                             │
│      55,000 원              │
│      지난달과 같아요          │
│                             │
│  [ 이번 달은 안 냈어요 ]      │
│            [ 다음 ]          │
└─────────────────────────────┘
```

- `이번 달은 안 냈어요` = 금액 0 + 사유 필수 (해지했거나 건너뛴 달)
- 금액을 고치면 사유 필수

#### 스텝 n+1 — 추가 지출

고정비에 없는, 그 달만의 지출. **이름부터 적는다.**

```
│  이번 달에 추가로 나간 돈이   │
│  있나요?                     │
│                             │
│  · 형 결혼식 축의금  300,000 │
│  · 냉장고 수리      120,000 │
│                             │
│       [ + 항목 추가 ]        │
│  [ 없어요 ]      [ 다음 ]    │
```

이름 / 분류 / 금액을 받는다. **사유는 안 받는다 — 이름 자체가 사유다.**

#### 스텝 n+2 — 이번 달 특이사항 (선택)

```
│  이번 달, 기억해둘 일이       │
│  있었나요?                   │
│                             │
│  ┌───────────────────────┐  │
│  │ 에어컨을 많이 틀어서    │  │
│  │ 전기세가 올랐다.        │  │
│  └───────────────────────┘  │
│  [ 건너뛰기 ]     [ 다음 ]   │
```

#### 스텝 n+3 — 확인 후 제출

```
수입                  3,450,000
고정비                -1,240,000
추가 지출               -420,000
────────────────────────────────
남은 돈                1,790,000

이번 달 달라진 것 3개
· 월급   +250,000  상여금 나옴
· 관리비  +60,000  에어컨 많이 틀었음
· 통신비  -12,000  요금제 변경
```

### 7.8 위저드 규칙

| 규칙 | 내용 |
|---|---|
| 자동 저장 | 스텝을 넘길 때마다 서버에 저장. 앱을 꺼도 이어서 작성 가능 (`cursor`) |
| 뒤로 가기 | 언제든 이전 스텝 수정 가능 |
| 사유 필수 조건 | `기본값이 있고` `입력값 ≠ 기본값`이면 사유 없이 다음으로 못 간다 |
| 사유 불필요 | 기본값이 없는 첫 달 · 추가 지출 · 금액이 같은 경우 |
| 사유 자동 삭제 | 금액을 원래 값으로 되돌리면 사유도 같이 지운다 |
| 제출 후 | 언제든 수정 가능. 장부의 `완성` 표시만 내려간다 |

## 8. 데이터 모델

원본은 `server/prisma/schema.prisma`다. 여기서는 관계와 의도만 적는다.

```
User ──┬─< Membership >─┬── Family
       │                ├─< FixedExpense   (사람별 고정비)
       │                └─< MemberEntry    (사람별 월간 기록)
       └ kakaoId | devKey

Family ──< MonthlyBook (가족 × YYYY-MM) ──< MemberEntry ──< EntryLine
```

| 테이블 | 한 줄 설명 |
|---|---|
| `User` | 카카오 계정 또는 개발용 계정 |
| `Family` | 가족. 6자리 `inviteCode` |
| `Membership` | 사용자 × 가족. `displayName`("아빠")이 여기 있다 |
| `FixedExpense` | **사람별** 고정비 항목. 지우면 `active=false` |
| `MonthlyBook` | 가족 × 특정 월. `OPEN` / `COMPLETE` (표시용 상태) |
| `MemberEntry` | 한 사람의 그 달 기록. `DRAFT`/`SUBMITTED`, `note`, `cursor` |
| `EntryLine` | 위저드의 한 줄. `INCOME` / `FIXED` / `EXTRA` |

### `EntryLine`이 이 앱의 전부다

```prisma
kind           INCOME | FIXED | EXTRA
fixedExpenseId 고정비 항목 참조 (장기 추이의 근거 — 이름이 바뀌어도 안 끊긴다)
name           그 달의 이름 스냅샷
category       그 달의 분류 스냅샷
plannedAmount  기본값 (지난달 실제 → 없으면 고정비 등록 금액 → 없으면 null)
plannedSource  LAST_MONTH | FIXED_DEFAULT | null   ← "지난달과 같아요"의 근거
actualAmount   사용자가 확정한 금액
changeReason   planned ≠ actual 일 때 필수
```

`name`·`category`를 참조가 아니라 **복사**해 두는 이유: 고정비 항목의 이름·분류를 나중에 바꿔도
과거 기록이 흔들리면 안 되기 때문이다. 반대로 `fixedExpenseId`는 참조로 남겨야
"이름이 바뀌어도 같은 항목"이 유지된다. **둘 다 필요하다.**

### 상태 전이

```
MemberEntry:  (없음) ──[my-entry]──▶ DRAFT ──[submit]──▶ SUBMITTED
                                       ▲                      │
                                       └──────[reopen]────────┘

MonthlyBook:  OPEN ⇄ COMPLETE     전원 SUBMITTED 이면 COMPLETE
              (refreshBookStatus 한 군데에서만 판단한다)
```

## 9. API

모든 응답은 JSON. 에러는 `{ code, message }`이고 `message`는 사용자에게 그대로 보여줘도 되는 한국어다.
인증이 필요한 요청은 `Authorization: Bearer <JWT>`.

| 구분 | 메서드 · 경로 | 설명 |
|---|---|---|
| 인증 | `GET /auth/config` | `{ kakao, dev }` — 로그인 화면이 그릴 버튼 결정 |
| | `GET /auth/kakao/start?returnUrl=` | 카카오 동의 화면으로 302 |
| | `GET /auth/kakao/callback?code&state` | 코드 교환 후 `returnUrl?token=`으로 302 |
| | `POST /auth/dev` | `{ name }` → `{ token }`. `DEV_LOGIN=true`일 때만 |
| | `GET /me` | 내 정보 + 속한 가족 목록 |
| 가족 | `GET /categories` | 분류 고정 목록 9개 |
| | `POST /families` | `{ name, displayName }` → 생성(OWNER) |
| | `POST /families/join` | `{ inviteCode, displayName }` |
| | `GET /families/:familyId` | 가족 + 구성원 + 초대코드 |
| | `POST /families/:familyId/invite-code` | 초대코드 재발급 (**OWNER**) |
| | `PATCH /families/:familyId/me` | 내 표시 이름 변경 |
| 고정비 | `GET /families/:familyId/fixed-expenses` | **사람별로 묶인** 목록 + 합계 |
| | `POST /families/:familyId/fixed-expenses` | `{ membershipId, name, category, defaultAmount, dayOfMonth? }` |
| | `PATCH /fixed-expenses/:id` | 부분 수정 |
| | `DELETE /fixed-expenses/:id` | `active=false` |
| 월 장부 | `GET /families/:familyId/books/:yearMonth` | 홈 — 장부 상태 + 사람별 진행 현황 |
| | `POST /families/:familyId/books/:yearMonth/my-entry` | 내 기록 시작/이어열기. **프리필된 초안 반환** |
| | `GET /families/:familyId/books/:yearMonth/summary` | 그 달 요약 |
| | `POST /families/:familyId/books/:yearMonth/refresh` | 상태 재계산 (복구용) |
| 기록 | `GET /entries/:id` | 내 기록 한 벌 (줄 전체) |
| | `PATCH /entries/:id` | `{ note?, cursor? }` |
| | `PATCH /entries/:id/lines/:lineId` | `{ actualAmount, changeReason? }` — **사유 규칙이 강제되는 자리** |
| | `POST /entries/:id/lines` | `{ name, category, actualAmount }` — 추가 지출 |
| | `DELETE /entries/:id/lines/:lineId` | 추가 지출만 삭제 가능 |
| | `POST /entries/:id/submit` | 제출 → `{ entry, bookStatus }` |
| | `POST /entries/:id/reopen` | 다시 열기 |

### v0.1에서 추가·수정할 API

| 메서드 · 경로 | 내용 |
|---|---|
| `GET /families/:familyId/trend?months=12` | 추이 탭. 월별 `{ yearMonth, income, fixedTotal, extraTotal, surplus, submittedCount, memberCount }` |

### 에러 코드

| 코드 | 상태 | 언제 |
|---|---|---|
| `UNAUTHORIZED` | 401 | 토큰 없음/만료 |
| `FORBIDDEN` | 403 | 남의 가족·남의 기록 |
| `NOT_FOUND` | 404 | 없는 초대코드·항목 |

| `FUTURE_MONTH` | 400 | 아직 오지 않은 달의 장부 |
| `VALIDATION` | 400 | zod 검증 실패 |

## 10. MVP 성공 기준

기술 스택 선택 이유와 개발 환경은 `README.md`에 있다. 검증은 `server/scripts/smoke.mjs`가
아래 시나리오를 그대로 따라간다.

1. 가족 2명이 각자 기기에서 카카오로 로그인해 **같은 가족**에 들어간다
2. 각자 고정비를 3개 이상 등록한다 — *여기까지가 엑셀의 '템플릿 만들기'다. 딱 한 번만 한다*
3. 각자 8월 기록을 스텝을 밟아 제출한다 — 최소 1개는 금액을 바꾸고 사유를 적는다
4. 8월 요약이 열린다 (한 명만 제출했어도 열리되, 누가 안 적었는지 같이 보인다)
5. **9월에 다시 기록을 시작하면 8월에 적은 금액이 기본값으로 깔려 있다**
6. 추이 탭에 8월·9월 두 점이 찍힌다

### 진짜 성공 기준은 5번이다

두 번째 달부터 이 앱은 **"적는 앱"이 아니라 "확인하는 앱"**이 된다.
엑셀에서는 시트를 복사하는 순간 값이 다 지워졌지만, 여기서는 **이미 채워진 채로 열린다.**
사용자가 할 일은 입력이 아니라 **다른 줄만 고치는 것**이다.

### 이 MVP로 알아내려는 것

MVP를 만드는 목적은 기능을 완성하는 게 아니라 **아래 질문의 답을 얻는 것**이다.
답이 나오면 v0.2 범위가 정해진다.

- 매달 실제로 다시 여는가? **어느 달에 처음 건너뛰는가?**
- 사유를 진짜로 적는가, 아니면 "그냥"이라고 치고 넘기는가?
- 가족 중 몇 명이 실제로 쓰는가? 한 명만 쓰게 되면 그건 개인 앱인가?
- 추가 지출이 매달 몇 개나 생기는가? (많으면 개인 가계부가 진짜 필요하다는 신호)
- 추이 화면을 보긴 보는가?
- 그래서 **엑셀로 돌아가지 않게 되는가?** 이게 최종 판정이다
